2 ЗАВДАННЯ
Ознайомитися з процесом розробки мобільного застосунку для платформи Android з використанням сучасних архітектурних підходів. Отримати практичні навички реалізації мобільного клієнта у складі розподіленої IoT-системи, що взаємодіє з серверною частиною через REST API.
Розробити Android-застосунок Plant Care System на основі Kotlin та Jetpack Compose як частину системи моніторингу та догляду за кімнатними рослинами. Застосунок повинен забезпечувати автентифікацію користувачів, CRUD-операції над рослинами, перегляд даних з IoT-сенсорів, фонову перевірку стану рослин з надсиланням локальних push-сповіщень, а також локалізацію інтерфейсу українською та англійською мовами.
Звіт повинен містити: UML-діаграму прецедентів (Use Case Diagram), UML-діаграму компонентів (Component Diagram), діаграму пакетів (Package Diagram), діаграму діяльності (Activity Diagram), опис прийнятих інженерних рішень та опис будови застосунку та його взаємодії з іншими частинами системи.

3. ОПИС ВИКОНАНОЇ РОБОТИ
Розроблено повнофункціональний Android-застосунок Plant Care для моніторингу та догляду за кімнатними рослинами через IoT-датчики. Застосунок є мобільним клієнтом системи Plant Care System і взаємодіє з готовим серверним API на Node.js/Express/PostgreSQL. Реалізовано сім екранів, автентифікацію через JWT, CRUD-операції для рослин, перегляд показань сенсорів з графіками, фоновий WorkManager-worker для моніторингу та локальні push-сповіщення.

3.2 Опис екранів застосунку

Застосунок містить сім екранів, що утворюють замкнений навігаційний граф:
–	SplashScreen – перевіряє наявність JWT-токену у DataStore при запуску і автоматично перенаправляє або на HomeScreen (токен є), або на LoginScreen (токен відсутній).
–	LoginScreen – форма входу з полями email та password. Після успішної автентифікації токен зберігається у DataStore, користувач переходить на HomeScreen.
–	RegisterScreen – форма реєстрації з полями email, ім'я, прізвище, пароль. Після реєстрації користувач повертається на LoginScreen.
–	HomeScreen – список рослин поточного користувача у вигляді карток PlantStatusCard із кольоровим індикатором стану (NORMAL / NEEDS_ATTENTION / CRITICAL). Список оновлюється при кожному поверненні на екран через repeatOnLifecycle(RESUMED). Підтримується Pull-to-Refresh.
–	PlantDetailScreen – детальна інформація про рослину, список активних сенсорів (SensorChip), кастомний лінійний графік (LineChart via Canvas) показань за тиждень/місяць, порогові значення, кнопки редагування та видалення.
–	AddPlantScreen – форма додавання або редагування рослини з Dropdown для вибору типу рослини. Режим редагування визначається через savedStateHandle.get<Int>("plantId")?.takeIf { it > 0 }.
–	SettingsScreen – перемикання мови (UA/EN) через AppCompatDelegate, вибір сезонного режиму, toggle сповіщень, повзунок інтервалу перевірки, кнопка виходу з системи.

3.7 Прийняті інженерні рішення

JWT-автентифікація через AuthInterceptor. Токен зберігається у DataStore Preferences (не SharedPreferences) для асинхронного доступу. AuthInterceptor автоматично додає заголовок Authorization: Bearer {token} до всіх запитів, окрім /auth/login та /auth/register. При отриманні відповіді 401 інтерцептор видаляє токен через dataStore.edit { it.remove(TOKEN) } та емітить подію у AuthEventBus (SharedFlow<Unit>). NavGraph підписується на цей flow через LaunchedEffect і здійснює навігацію на LoginScreen з очищенням back-стеку (popUpTo(0)).

Hilt Workers для фонових задач. PlantCareApp реалізує Configuration.Provider і надає HiltWorkerFactory, що дозволяє впроваджувати залежності у SensorCheckWorker через @AssistedInject. Автоматична ініціалізація WorkManager вимкнена у AndroidManifest.xml (tools:node="remove"), щоб уникнути конфлікту зі стандартною фабрикою.

safeApiCall<T> – узагальнена функція-обгортка над Retrofit. Обробляє три сценарії: success=true і data != null → Result.success(data); success=true і data == null (logout, delete) → Result.success(Unit as T); HTTP-виняток → парсинг тіла помилки через Moshi і Result.failure(Exception(message)).

Кастомний Moshi-адаптер для Unit. Оскільки Moshi не має вбудованого адаптера для типу Unit, у AppModule.provideMoshi() зареєстровано анонімний JsonAdapter<Unit>, який при десеріалізації викликає reader.skipValue() і повертає Unit. Це дозволяє коректно обробляти відповіді ApiResponse<Unit> для ендпоінтів DELETE /api/my-plants/{id} та POST /api/auth/logout.

Перемикання локалі при запуску. setApplicationLocales() викликається не лише при зміні мови у налаштуваннях, але й у PlantCareApp.onCreate() через applySavedLocale(): функція читає збережений код мови з DataStore синхронно через runBlocking і застосовує його до AppCompatDelegate. MainActivity успадковує AppCompatActivity (не ComponentActivity), що є обов'язковим для коректного перезапуску Activity при зміні локалі.

Оновлення списку рослин після навігації. HomeViewModel не має init-блоку з автозавантаженням – замість цього HomeScreen використовує LaunchedEffect з repeatOnLifecycle(Lifecycle.State.RESUMED), що гарантує перезавантаження списку при кожному поверненні на екран після додавання, редагування або видалення рослини.

Кастомний LineChart через Canvas. Бібліотека Vico 2.0.0 була видалена через несумісність API (CartesianChartModelProducer відсутній). Замість неї реалізовано кастомний @Composable LineChart, який малює графік показань сенсорів безпосередньо на Canvas з підтримкою вибору діапазону (тиждень/місяць).

network_security_config.xml дозволяє cleartext-трафік лише для 10.0.2.2 (хост-машина з емулятора), що є безпечнішим за глобальне вимкнення перевірки TLS. Base URL: http://10.0.2.2:3000/api.  Інтеграція з IoT (Arduino). Бекенд отримує дані від Arduino-пристрою через ендпоінт POST /api/sensor-data/bulk. Arduino зчитує показання з датчиків DHT22 (вологість/температура) та BH1750 (освітленість) і надсилає масив записів. SensorCheckWorker у мобільному застосунку зчитує ці дані через GET /api/sensors/{sensorId}/data і порівнює з оптимальними значеннями типу рослини.  Таблиця plant_actions у базі даних. Бекенд підтримує таблицю plant_actions (action_id, plant_id, user_id, action_type, action_value, action_duration, notes, performed_at) для журналювання дій над рослинами: полив, освітлення, вентиляція, ручна перевірка, удобрення. Типи дій визначені як ENUM: watering, lighting, ventilation, manual_check, fertilizing.

4. ВИСНОВКИ
У ході виконання лабораторної роботи № 2 успішно розроблено повнофункціональний Android-застосунок Plant Care System з використанням Kotlin, Jetpack Compose та сучасних архітектурних підходів.
Реалізовано семиекранний мобільний клієнт із MVVM-архітектурою, JWT-автентифікацією через OkHttp-інтерцептор, повним CRUD-інтерфейсом для управління рослинами, відображенням показань IoT-сенсорів із кастомними графіками на Canvas, фоновим моніторингом через WorkManager з Hilt-інтеграцією та локальними push-сповіщеннями про критичний стан рослин.
Впроваджено локалізацію інтерфейсу українською та англійською мовами з коректним перемиканням при старті через AppCompatDelegate. Вирішено 10 нетривіальних технічних проблем, зокрема: обробка Unit-відповідей Moshi, фіксація 401-logout через SharedFlow, коректне оновлення списку через repeatOnLifecycle, видалення несумісної бібліотеки Vico та її заміна на кастомний Canvas-компонент.
Застосунок взаємодіє з серверною частиною системи (Node.js/Express/PostgreSQL) через захищений REST API із JWT-автентифікацією і готовий до інтеграції з реальними IoT-пристроями.

1. Запит (prompt) щодо обробки 401 Unauthorized через SharedFlow:
Я розробляю Android-застосунок на Kotlin + Jetpack Compose + Retrofit. У мене є OkHttp-інтерцептор AuthInterceptor, який при отриманні відповіді 401 повинен видаляти JWT-токен з DataStore та ініціювати навігацію на LoginScreen. Проблема: інтерцептор виконується у фоновому потоці OkHttp і не має доступу до NavController. Як правильно організувати комунікацію між AuthInterceptor та NavGraph у Compose? Архітектура: MVVM, Hilt DI, NavHost у MainActivity.
Отримана відповідь:
Для вирішення цієї задачі рекомендується патерн EventBus через SharedFlow. Створіть singleton-об'єкт AuthEventBus з MutableSharedFlow<Unit>. AuthInterceptor викликає AuthEventBus.emit401() через runBlocking після видалення токену. NavGraph підписується на цей flow через LaunchedEffect і виконує навігацію на LoginScreen з popUpTo(0), що очищає весь back-стек. SharedFlow з replay=0 гарантує, що подія не буде оброблена повторно при рекомпозиції.
2. Запит (prompt) щодо інтеграції Hilt у WorkManager:
Я використовую WorkManager для фонового моніторингу сенсорів у Android-застосунку з Hilt DI. При спробі впровадити репозиторії у SensorCheckWorker через конструктор отримую RuntimeException під час виконання Worker. Як правильно налаштувати Hilt для ін'єкцій у CoroutineWorker? Що потрібно змінити в Application class та AndroidManifest?
Отримана відповідь:
Для коректної роботи Hilt з WorkManager необхідно виконати три кроки. По-перше, Application class повинен реалізовувати інтерфейс Configuration.Provider і надавати HiltWorkerFactory через @Inject. По-друге, у AndroidManifest.xml необхідно вимкнути автоматичну ініціалізацію WorkManager через tools:node="remove" для WorkManagerInitializer, щоб уникнути конфлікту зі стандартною фабрикою. По-третє, сам Worker анотується @HiltWorker, а залежності впроваджуються через @AssistedInject з обов'язковими параметрами Context та WorkerParameters, анотованими @Assisted.

1  package com.plantcare.mobile.data.api
2  
3  import androidx.datastore.core.DataStore
4  import androidx.datastore.preferences.core.Preferences
5  import androidx.datastore.preferences.core.edit
6  import com.plantcare.mobile.data.local.DataStoreKeys
7  import com.plantcare.mobile.util.AuthEventBus
8  import kotlinx.coroutines.flow.firstOrNull
9  import kotlinx.coroutines.flow.map
10 import kotlinx.coroutines.runBlocking
11 import okhttp3.Interceptor
12 import okhttp3.Response
13 
14 class AuthInterceptor(
15     private val dataStore: DataStore<Preferences>
16 ) : Interceptor {
17 
18     private val skipPaths = listOf("/auth/login", "/auth/register")
19 
20     override fun intercept(chain: Interceptor.Chain): Response {
21         val request = chain.request()
22         val path = request.url.encodedPath
23         val shouldSkip = skipPaths.any { path.contains(it) }
24 
25         val newRequest = if (shouldSkip) { request } else {
26             val token = runBlocking {
27                 dataStore.data.map { it[DataStoreKeys.TOKEN] }.firstOrNull()
28             }
29             if (token != null) {
30                 request.newBuilder()
31                     .addHeader("Authorization", "Bearer $token")
32                     .build()
33             } else { request }
34         }
35 
36         val response = chain.proceed(newRequest)
37 
38         if (response.code == 401 && !shouldSkip) {
39             runBlocking { dataStore.edit { it.remove(DataStoreKeys.TOKEN) } }
40             AuthEventBus.emit401()
41         }
42         return response
43     }
44 }

6  suspend fun <T> safeApiCall(call: suspend () -> ApiResponse<T>): Result<T> {
7      return try {
8          val response = call()
9          if (response.success) {
10             val data = response.data
11             if (data != null) {
12                 Result.success(data)
13             } else {
14                 // Unit responses (logout, delete): success=true, data=null
15                 @Suppress("UNCHECKED_CAST")
16                 Result.success(Unit as T)
17             }
18         } else {
19             Result.failure(Exception(response.message ?: "Помилка сервера"))
20         }
21     } catch (e: HttpException) {
22         val bodyString = e.response()?.errorBody()?.string()
23         val message = try {
24             errorAdapter.fromJson(bodyString ?: "")?.error ?: e.message()
25         } catch (_: Exception) { e.message() }
26         Result.failure(Exception(message))
27     } catch (e: Exception) {
28         Result.failure(e)
29     }
30 }
