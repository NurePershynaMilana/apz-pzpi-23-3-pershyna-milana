3. ОПИС ВИКОНАНОЇ РОБОТИ
Реалізовано горизонтальне масштабування бекенду системи Plant Care за допомогою Kubernetes. Бекенд є Node.js Express API з базою даних PostgreSQL, контейнеризований у Docker. Для розгортання розроблено папку k8s з 9 YAML-маніфестами та скрипт навантажувального тестування Locust. Продемонстровано автоматичне масштабування від 1 до 5 реплік через HorizontalPodAutoscaler та зворотне масштабування до 0 активних запитів.

3.2 Опис Kubernetes-маніфестів
Конфігурація кластера складається з 9 YAML-файлів у папці k8s/, кожен з яких відповідає за окремий аспект розгортання системи.
–	00-namespace.yaml — створює ізольований простір імен plant-care, у якому згруповано всі ресурси кластера.
–	01-secrets.yaml — зберігає чутливі дані: пароль бази даних, рядок підключення та JWT-секрет як Kubernetes Secret.
–	02-configmap.yaml — містить нечутливі змінні середовища: хост бази даних, порт, Node-середовище.
–	03-postgres-init-configmap.yaml — містить SQL-схему та початкові дані, які монтуються в PostgreSQL-под при першому запуску.
–	04-postgres-pvc.yaml — PersistentVolumeClaim, що виділяє 1 ГБ стійкого сховища для PostgreSQL.
–	05-postgres.yaml — Deployment PostgreSQL та ClusterIP Service postgres-service зі стабільним DNS-ім'ям для бекенду.
–	06-backend-deployment.yaml — Deployment бекенду з початковою 1 реплікою, init-контейнером очікування PostgreSQL та лімітами CPU.
–	07-backend-service.yaml — NodePort Service на порті 30000 з автоматичним балансуванням трафіку між репліками.
–	08-hpa.yaml — HorizontalPodAutoscaler, що перевіряє CPU кожні 15 секунд та масштабує від 1 до 5 реплік при перевищенні порогу 50%.
3.3 Опис скрипту навантажувального тестування
Для навантажувального тестування розроблено скрипт locustfile.py, що симулює поведінку реальних користувачів системи Plant Care. Скрипт визначає клас BackendUser, який виконує запити до різних ендпоінтів API із затримкою від 1 до 3 секунд між запитами.
Розподіл задач (weight) побудований так, щоб максимально навантажити сервер: перевірка стану (GET /health) — 30%; запит типів рослин (GET /plant-types) — 25%; автентифіковані запити рослин (GET /my-plants) — 30%; операція логіну (POST /auth/login) — 15%. Операція логіну є найбільш CPU-навантаженою через bcrypt-хешування паролів, що провокує швидке зростання завантаженості процесора і спрацювання HPA.

from locust import HttpUser, task, between

class BackendUser(HttpUser):
    wait_time = between(1, 3)

    @task(3)
    def health_check(self):
        self.client.get('/health')

    @task(3)
    def get_plants(self):
        self.client.get('/my-plants', headers=self.auth_headers())

    @task(1)
    def login(self):
        self.client.post('/auth/login',
            json={'email': 'test@test.com', 'password': 'test1234'})

3.4 Результати навантажувального тестування
Навантажувальне тестування проводилось при 50 одночасних користувачах зі швидкістю появи 5 користувачів на секунду (spawn rate). Тестування виконувалось у три етапи: базовий (1 репліка), ручне масштабування (3 репліки) та автоматичне масштабування через HPA (до 5 реплік). Результати наведені у таблиці 3.2.
Таблиця 3.2 – Результати навантажувального тестування
Кількість реплік	RPS (запитів/сек)	Median (мс)	95%ile (мс)	Стан системи
1 (базовий)	~12	~2600	~5800	Насичений под
3 (ручне)	~28	~550	~1200	Нормальна робота
5 (HPA авто)	~42	~380	~900	Оптимальна продуктивність
1 (після зупинки)	~12	~2500	~5600	Автоматичне зменшення

Аналіз результатів показує чітку лінійну залежність між кількістю реплік та пропускною здатністю системи. При збільшенні кількості подів з 1 до 5 RPS зріс у 3,5 рази (з 12 до 42 запитів/сек), а медіанний час відповіді зменшився у 6,8 рази (з 2600 до 380 мс). Це підтверджує ефективність горизонтального масштабування для даного типу навантаження.
3.5 Прийняті інженерні рішення
Init-контейнер для PostgreSQL. Deployment бекенду містить init-контейнер на базі busybox, який виконує команду nslookup postgres-service у циклі до її успішного виконання. Це гарантує, що основний контейнер бекенду стартує лише після того, як PostgreSQL повністю готовий до прийому з'єднань, що запобігає помилкам підключення під час ініціалізації.

Ліміти CPU як умова HPA. Явне визначення resources.requests.cpu та resources.limits.cpu у специфікації контейнера є обов'язковою умовою роботи HorizontalPodAutoscaler. Без цих значень метрики API Kubernetes не може розрахувати відсоток використання CPU відносно запиту, і HPA не спрацьовує. Встановлено запит 100m та ліміт 200m (мілісекунди CPU).

PersistentVolumeClaim для PostgreSQL. Замість використання emptyDir (що призводить до втрати даних при перезапуску поду) для PostgreSQL виділено PVC розміром 1 ГБ. Це забезпечує збереження даних між перезапусками подів та оновленнями deployment-у.

Стратегія масштабування вниз. HPA налаштований з periodSeconds: 15 для scaleUp та stabilizationWindowSeconds: 60 для scaleDown. Затримка при масштабуванні вниз запобігає видаленню реплік при короткочасному падінні трафіку, що знижує ризик деградації продуктивності при пульсуючому навантаженні.

Розроблено 9 YAML-маніфестів, що охоплюють повний цикл розгортання: ізоляцію ресурсів (Namespace), безпечне зберігання конфігурації (Secret, ConfigMap), стійке сховище (PVC), розгортання сервісів (Deployment) та балансування навантаження (NodePort Service). Реалізовано автоматичне масштабування через HorizontalPodAutoscaler з пороговим значенням CPU 50% та діапазоном від 1 до 5 реплік.

Єдиним незмасштабованим компонентом залишається PostgreSQL — у продуктивному середовищі його слід масштабувати окремо за допомогою read-реплік або пулера з'єднань. Автоматичне масштабування вниз після зупинки тестового навантаження підтвердило коректну роботу механізму стабілізації HPA.

1. Запит (prompt) щодо налаштування HPA для Node.js бекенду:
Я розгортаю Node.js Express API у Kubernetes через minikube. Хочу налаштувати HorizontalPodAutoscaler щоб він автоматично масштабував бекенд від 1 до 5 реплік при навантаженні. Які ліміти CPU потрібно встановити у Deployment щоб HPA коректно рахував відсоток використання?
Отримана відповідь:
Для коректної роботи HPA необхідно обов'язково вказати resources.requests.cpu у специфікації контейнера — саме від цього значення HPA рахує відсоток. Рекомендується встановити request: 100m та limit: 200m. Без request HPA не матиме базового значення для розрахунку і не буде спрацьовувати. Додатково потрібно переконатись що metrics-server встановлений у кластері — для minikube це робиться через minikube addons enable metrics-server.

2. Запит (prompt) щодо написання скрипту Locust для провокування CPU-навантаження:
Я хочу написати locustfile.py для навантажувального тестування Node.js/Express бекенду Plant Care System. Мета — спровокувати достатнє CPU-навантаження, щоб HorizontalPodAutoscaler спрацював і збільшив кількість реплік з 1 до 5. Бекенд має ендпоінти: GET /health, GET /plant-types, GET /my-plants (потребує JWT), POST /auth/login (використовує bcrypt). Як правильно розподілити вагу задач щоб максимально навантажити CPU?
Отримана відповідь:
Для максимального CPU-навантаження варто зробити акцент на POST /auth/login, оскільки bcrypt є навмисно повільною операцією і створює найбільше навантаження на процесор. Рекомендований розподіл: login з вагою 2-3, get_plants з вагою 3 (потребує JWT-верифікації), health та plant-types з вагою 1. Для автентифікованих запитів слід реалізувати метод on_start, який виконує логін один раз при ініціалізації користувача та зберігає токен у headers. Кількість користувачів 50 зі spawn rate 5 достатньо для того щоб 1 репліка вийшла за 50% CPU і HPA почав масштабування протягом 1-2 хвилин.

Лістинг Б.4 – 03-postgres-init-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: postgres-init
  namespace: plant-care
data:
  01-init.sql: |
    DROP TABLE IF EXISTS plant_actions CASCADE;
    DROP TABLE IF EXISTS sensor_data CASCADE;
    DROP TABLE IF EXISTS sensors CASCADE;
    DROP TABLE IF EXISTS plants CASCADE;
    DROP TABLE IF EXISTS plant_types CASCADE;
    DROP TABLE IF EXISTS users CASCADE;

    DO $$ BEGIN
      IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'user_role') THEN
        CREATE TYPE user_role AS ENUM ('user', 'admin');
      END IF;
    END $$;

    DO $$ BEGIN
      IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'action_type') THEN
        CREATE TYPE action_type AS ENUM ('watering', 'lighting', 'ventilation', 'manual_check', 'fertilizing');
      END IF;
    END $$;

    CREATE TABLE users (
        user_id SERIAL PRIMARY KEY,
        email VARCHAR(255) NOT NULL UNIQUE,
        first_name VARCHAR(100) NOT NULL,
        last_name VARCHAR(100) NOT NULL,
        password_hash VARCHAR(255) NOT NULL,
        role user_role DEFAULT 'user',
        last_login TIMESTAMP,
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );

    CREATE TABLE plant_types (
        plant_type_id SERIAL PRIMARY KEY,
        name VARCHAR(100) NOT NULL,
        optimal_humidity FLOAT CHECK (optimal_humidity BETWEEN 0 AND 100),
        optimal_temperature FLOAT CHECK (optimal_temperature BETWEEN 5 AND 40),
        optimal_light INTEGER CHECK (optimal_light > 0),
        watering_frequency INTEGER CHECK (watering_frequency > 0)
    );

    CREATE TABLE plants (
        plant_id SERIAL PRIMARY KEY,
        user_id INTEGER NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
        plant_type_id INTEGER NOT NULL REFERENCES plant_types(plant_type_id),
        name VARCHAR(100) NOT NULL,
        location VARCHAR(100) NOT NULL,
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );

    CREATE TABLE sensors (
        sensor_id SERIAL PRIMARY KEY,
        plant_id INTEGER NOT NULL REFERENCES plants(plant_id) ON DELETE CASCADE,
        sensor_type VARCHAR(20) CHECK (sensor_type IN ('humidity', 'temperature', 'light')),
        hardware_id VARCHAR(50) NOT NULL UNIQUE,
        is_active BOOLEAN DEFAULT TRUE
    );

    CREATE TABLE sensor_data (
        data_id SERIAL PRIMARY KEY,
        sensor_id INTEGER NOT NULL REFERENCES sensors(sensor_id) ON DELETE CASCADE,
        value FLOAT NOT NULL,
        timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );

    CREATE TABLE plant_actions (
        action_id SERIAL PRIMARY KEY,
        plant_id INTEGER NOT NULL REFERENCES plants(plant_id) ON DELETE CASCADE,
        user_id INTEGER NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
        action_type action_type NOT NULL,
        action_value VARCHAR(200),
        action_duration INTEGER DEFAULT 0,
        notes TEXT,
        performed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );

    CREATE INDEX idx_users_email ON users(email);
    CREATE INDEX idx_users_role ON users(role);
    CREATE INDEX idx_plants_user ON plants(user_id);
    CREATE INDEX idx_plants_type ON plants(plant_type_id);
    CREATE INDEX idx_sensors_plant ON sensors(plant_id);
    CREATE INDEX idx_sensor_data_sensor ON sensor_data(sensor_id);

  4. Scale to 5 pods → RPS increases further
"""

from locust import HttpUser, task, between, events
import json
import logging

logger = logging.getLogger(__name__)

# Test credentials from seed data
TEST_USERS = [
    {"email": "ivan.petrenko@email.com", "password": "password123"},
    {"email": "maria.kovalenko@email.com", "password": "password456"},
    {"email": "oleh.shevchenko@email.com", "password": "password789"},

class PlantCareUser(HttpUser):
    """
    Simulates a real user hitting the Plant Care API.
    Mix of lightweight reads, heavier DB queries, and auth calls.
    """
    wait_time = between(0.5, 2)

    def on_start(self):
        """Called once per simulated user on startup — log in and cache the JWT."""
        import random
        creds = random.choice(TEST_USERS)
        self.token = None
        self.user_email = creds["email"]

        with self.client.post(
            "/api/auth/login",
            json=creds,
            catch_response=True,
            name="POST /api/auth/login [startup]",
        ) as resp:
            if resp.status_code == 200:
                data = resp.json()
                # Handle both {token: ...} and {data: {token: ...}} response shapes
                self.token = data.get("token") or (data.get("data") or {}).get("token")
                if self.token:
                    resp.success()
                else:
                    resp.failure("Login response had no token field")
            else:
                resp.failure(f"Login failed: {resp.status_code} {resp.text[:200]}")

    def auth_headers(self):
        return {"Authorization": f"Bearer {self.token}"} if self.token else {}

    # ------------------------------------------------------------------ #
    # Lightweight endpoints — high weight, no auth needed
    # ------------------------------------------------------------------ #

    @task(4)
    def health_check(self):
        """Fastest possible endpoint — good baseline for measuring pod throughput."""
        self.client.get("/health", name="GET /health")

    @task(6)
    def get_plant_types(self):
        """Read-only catalog — no auth, small table, very fast."""
        self.client.get("/api/plant-types", name="GET /api/plant-types")

    # ------------------------------------------------------------------ #
    # Authenticated read endpoints — moderate weight
    # ------------------------------------------------------------------ #

    @task(5)
    def get_my_plants(self):
        """Returns authenticated user's plants — JWT decode + DB join."""
        self.client.get(
            "/api/my-plants",
            headers=self.auth_headers(),
            name="GET /api/my-plants",
        )

    @task(4)
    def get_all_plants(self):
        """Admin/general plant list."""
        self.client.get(
            "/api/plants",
            headers=self.auth_headers(),
            name="GET /api/plants",
        )

    @task(3)
    def get_sensors(self):
        """List sensors — DB query with auth overhead."""
        self.client.get(
            "/api/sensors",
            headers=self.auth_headers(),
            name="GET /api/sensors",
        )

    @task(3)
    def get_sensor_data(self):
        """Heavier query — time-series table, tests DB throughput."""
        self.client.get(
            "/api/sensor-data",
            headers=self.auth_headers(),
            name="GET /api/sensor-data",
        )

    # ------------------------------------------------------------------ #
    # Write / CPU-heavy endpoints — low weight
    # ------------------------------------------------------------------ #

    @task(1)
    def login_again(self):
        """bcrypt compare on every call — most CPU-intensive operation."""
        import random
        creds = random.choice(TEST_USERS)
        with self.client.post(
            "/api/auth/login",
            json=creds,
            catch_response=True,
            name="POST /api/auth/login",
        ) as resp:
            if resp.status_code == 200:
                resp.success()
            else:
                resp.failure(f"{resp.status_code}")
