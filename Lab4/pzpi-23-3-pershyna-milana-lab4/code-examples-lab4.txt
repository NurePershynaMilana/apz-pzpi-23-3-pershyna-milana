Під час виконання лабораторної роботи було використано інструмент штучного інтелекту Claude:
•	назва інструменту та версія: Claude Sonnet 4.6
•	мета використання: отримання рекомендацій щодо налаштування HPA, написання init-контейнера та оптимізації locustfile.py для провокування CPU-навантаження
•	внесок автора: отримані відповіді адаптовані під конкретну архітектуру Plant Care System, скориговано ліміти CPU, перевірено сумісність версій Kubernetes API та виправлено init-контейнер під особливості minikube


1. Запит (prompt) щодо налаштування HPA для Node.js бекенду:
Я розгортаю Node.js Express API у Kubernetes через minikube. Хочу налаштувати HorizontalPodAutoscaler щоб він автоматично масштабував бекенд від 1 до 5 реплік при навантаженні. Які ліміти CPU потрібно встановити у Deployment щоб HPA коректно рахував відсоток використання?

Отримана відповідь:
Для коректної роботи HPA необхідно обов'язково вказати resources.requests.cpu у специфікації контейнера — саме від цього значення HPA рахує відсоток. Рекомендується встановити request: 100m та limit: 200m. Без request HPA не матиме базового значення для розрахунку і не буде спрацьовувати. Додатково потрібно переконатись що metrics-server встановлений у кластері — для minikube це робиться через minikube addons enable metrics-server.

2. Запит (prompt) щодо написання скрипту Locust для провокування CPU-навантаження:
Я хочу написати locustfile.py для навантажувального тестування Node.js/Express бекенду Plant Care System. Мета — спровокувати достатнє CPU-навантаження, щоб HorizontalPodAutoscaler спрацював і збільшив кількість реплік з 1 до 5. Бекенд має ендпоінти: GET /health, GET /plant-types, GET /my-plants (потребує JWT), POST /auth/login (використовує bcrypt). Як правильно розподілити вагу задач щоб максимально навантажити CPU?

Отримана відповідь:
Для максимального CPU-навантаження варто зробити акцент на POST /auth/login, оскільки bcrypt є навмисно повільною операцією і створює найбільше навантаження на процесор. Рекомендований розподіл: login з вагою 2-3, get_plants з вагою 3 (потребує JWT-верифікації), health та plant-types з вагою 1. Для автентифікованих запитів слід реалізувати метод on_start, який виконує логін один раз при ініціалізації користувача та зберігає токен у headers. Кількість користувачів 50 зі spawn rate 5 достатньо для того щоб 1 репліка вийшла за 50% CPU і HPA почав масштабування протягом 1-2 хвилин.
